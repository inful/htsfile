refactor(cmd/htsfile): consolidate translate.go streaming loop (v0.18.2)

Closes the architecture review's item #4. The four
translate.go subcommand functions (runSAMToBAM /
runBAMToSAM / runVCFToBCF / runBCFToVCF) each
implemented the same "decode header → write header →
stream records" loop verbatim, with only the
concrete decoder/encoder types and the convert
functions differing.

runTranslateStream[DH, EH, DR, ER any]
accepts seven closures (readHeader, readRecord,
convertHeader, writeHeader, convertRecord,
writeRecord, finalise) and implements the shared
loop once. Each call site binds a single decoder
and encoder pair and threads them through the
helper.

The helper is closure-based rather than
interface-based because the four encoders use
different method names for the same operations
(`WriteHeader`/`Close` for bam and bcf;
`EncodeHeader`/`Flush` for sam and vcf). A single
interface would force one naming convention on
every package; closures don't.

Per-function line counts dropped from ~25 to ~14.
The shared pattern (header parse → header convert
→ header write → record loop → finalise) lives in
exactly one place.

Also dropped: the dead `var _ = bytes.NewReader`
sentinel and its `bytes` import.

All four subcommands retain their public signatures
and observable behaviour. Existing tests pass:
- TestSAMToBAMAndBack
- TestVCFToBCFAndBack
- TestCLIPipeline_VCFToBCFAndBack

go test -race -count=1 ./... is green; golangci-lint
run ./... reports 0 issues; make fmt-check is clean.

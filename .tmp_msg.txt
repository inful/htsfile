fix(vcf): complete the reserved-key tables and run the check by default (T4.25-T4.27, v0.20.0)

Closes the three gaps the v0.19.0 audit found. All three
land in the same two files and their tests cross-cover
each other, so this ships as one release rather than
three; splitting would have produced intermediate commits
that do not compile.

T4.25 — tables incomplete.

reservedInfoKeys carried only the v4.5-new subset. All 21
keys from the spec's Reserved INFO keys table (lines
460-480) were absent: AA, AC, AD, ADF, ADR, AF, AN, BQ,
CIGAR, DB, DP, END, H2, H3, MQ, MQ0, NS, SB, SOMATIC,
VALIDATED, 1000G. reservedFormatKeys was missing 18 of the
Reserved genotype keys table (lines 534-596): AD, ADF,
ADR, DP, EC, LEN, FT, GQ, GT, HQ, LA, MQ, PP, PQ, PS.
checkReservedKeys skips unknown keys, so a header
declaring `##INFO=<ID=DP,Number=5,Type=String,...>` or
`##FORMAT=<ID=HQ,Number=G,Type=Float,...>` produced no
diagnostic in either mode.

T4.26 — nine FORMAT keys had the wrong Number or Type.

  LAA  spec `.` Integer   was `.` String
  LAD  spec LR  Integer   was `.` String
  LADF spec LR  Integer   was `.` String
  LADR spec LR  Integer   was `.` String
  LEC  spec LA  Integer   was `.` Integer
  LGL  spec LG  Float     was G  String
  LGP  spec LG  Float     was G  String
  LPL  spec LG  Integer   was P  String
  LPP  spec LG  Integer   was G  Integer

All nine are local-allele keys whose Number should be
LA/LR/LG. LPL and LPP were also wrong on Type — they are
the phred-scaled likelihood and posterior, so Integer,
not Float (Float is LGL/LGP). The audit named only LAA,
LPL and LPP; diffing the whole table during the fix
turned up the other six.

This was a false-positive bug: ModeStrict warned against
files that follow the spec exactly. Only the header
metadata cross-check was affected — laaLenFor and
checkLAA already tolerated both wire forms.

T4.27 — gating contradicted its own doc comment.

HeaderChecks called checkReservedKeys only under
v.Mode == ModeStrict, while the function's doc comment
described a default-mode warning "the caller can promote
... by switching to ModeStrict". There was nothing to
promote. The gate now lives on the diagnostic rather than
the call: the check runs in both modes and still reports
SeverityWarning. A reserved key declared with the wrong
Number or Type is a header defect regardless of mode, and
the spec frames these keys as reserved "albeit optional".
HeaderChecks also preallocates issues to
len(h.Infos)+len(h.Formats).

Tests:

vcf/reserved_table_test.go (new) transcribes both spec
tables verbatim as specReservedInfo / specReservedFormat
and diffs the implementation against them, so the tables
cannot silently drift again. Five tests cover the table
contents, the absence of false positives on all 51
spec-correct declarations, 11 wrong declarations being
caught, and the ModeDefault gating.

TestIsReservedInfoKey and TestIsReservedFormatKey were
asserting the gap: both listed DP/AF/AC/NS and GT/DP as
keys that must NOT be reserved, the exact inverse of the
spec tables. That pinned the incomplete tables in place.
Rewritten to assert the spec tables, with genuinely
arbitrary keys (MN, RM, FOO, ZZZ) as the negatives.

The base-modification families (M / DPM / ADM, spec lines
556-588, all Number=M) stay out of the tables: they are
an open-ended key space resolved by MFamily.
